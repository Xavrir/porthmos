## B1. The owner key sends server-supplied calldata, so an API host compromise can take over any Safe. This falsifies the blast-radius claims, and TradeFlow adds two more paths that use the same pattern

- Proposed severity: High
- Source locator: S1 L814 (API host row: "Funds still cannot leave any Safe except through TradeFlow orders that owners funded"), S1 L801, S1 L301 ("returns the reserve floor update for the owner to sign, as the obligation flow does today"), S1 L306 ("The service only returns the calldata"), S1 L330 (`GET .../resolution` returns "Safe transaction calldata for the owner key to sign and send"). Verified pattern: S14 web/src/pages/Treasury.tsx L51-61, web/src/lib/identity.tsx L180-191 and L310-319.
- Scope link: TARGET T2 (key separation and blast radius, L789-815) and TARGET T1 (TradeFlow off-chain flow L301, L306, API L330, test T47).
- Broken requirement or necessary assumption: the threat model includes "a compromised server process" (S1 L529). The key separation table says that when the API host is compromised, funds can leave a Safe only through owner-funded orders. That claim holds only if the browser never sends `to`/`data` that it has not built or checked itself.
- Concrete failure scenario: An attacker controls the API process. A tenant owner with a burner key clicks "sign floor update" after an obligation change, or after a linked order (L301). The API returns `floorUpdate = {to: <tenant Safe>, data: execTransaction(to=<attacker>, value=0, data=<payload>, operation=1 DELEGATECALL, safeTxGas=0, ..., signatures = r=owner, s=0, v=1)}`. `signFloor` calls `sendTx(floorTx)`. `localTx` signs and sends it from the owner key. The pre-validated signature is valid because `msg.sender` is the owner and the threshold is 1 (S1 L214). The delegatecall runs attacker code in the Safe context: it moves all USDC, adds a module or owner, and redeems the vault shares. The confirmation dialog decodes the data with `FLOOR_ABI`. When decoding fails, it falls back to the computed reserve amount (Treasury.tsx L67-74). So the owner sees a plausible floor amount. The new TradeFlow `resolution?action=waive|refund` endpoint (L330) is a second path to the same takeover.
- Impact: Every tenant Safe whose owner clicks a server-assisted transaction button can be fully drained. A refund of escrowed funds to the Safe also goes to the attacker. This contradicts L801, L814 and mechanism 3 ("impossible by construction") under an in-scope adversary.
- Architecture disposition: EXTEND. The seam is the web transaction layer (`sendTx`/`localTx` in identity.tsx) and the TradeFlow resolution endpoint. AegisModule, PolicyRegistry and TradeEscrow need no change.
- Minimal design change: The browser builds every owner transaction itself, from addresses in the bundled deployments file (registry, TradeEscrow, MultiSendCallOnly) and typed parameters. For a floor update the parameters are the amount and `scheduleHash`. For a resolution they are `orderId`, the action and `index`. The API returns these parameters only, not calldata. As a guard, `sendTx` refuses any `to` that is not a pinned contract and any Safe `execTransaction` that it did not build. Change S1 L306 and L330 to "the service returns the parameters; the web builds the transaction". Add a row to the threat table.
- Acceptance check: A Vitest case (extend W-tests and T47) gives the floor-update and resolution flows an API response with `to = <Safe>` or a different selector. Before the change, `sendTx` is called with the attacker calldata (test fails). After the change, nothing is sent and the UI shows a refusal. A second case shows that a valid response produces calldata equal to a locally encoded `setReserveFloor`/`waive`/`refund` to the pinned address.
- Confidence: High. The code path is verified, and the TD explicitly reuses the "as the obligation flow does today" pattern.
- What evidence would disprove it: A check in `localSender.send` or elsewhere that limits `to` to pinned addresses and decodes the selector before signing. I did not find one in the files read.

## B2. Anyone can force a milestone into HELD and stop the automated release, because unauthenticated proof submissions with bad signatures become holds

- Proposed severity: High
- Source locator: S1 L302-307 (step 4 "sent by the issuer or supplier", step 7 "If a check fails, the milestone is HELD"), S1 L327 (`POST /proofs`: "Anyone, rate-limited per order"), S1 L429-430 (HELD reason codes include `ProofMismatch` and `BadIssuerSignature`; "After a hold, the agent does not ask for a release on a later proof for the same milestone until the owner confirms it"), S1 L332 (30 submissions per order per hour), S1 L1036 (T36).
- Scope link: TARGET T1 (milestone state machine, API, T36, demo per S5 section 17).
- Broken requirement or necessary assumption: The design assumes that only a meaningful proof can change milestone state. "The issuer signature is the authority" (L327), but the state machine lets a submission with no valid issuer signature create the hold.
- Concrete failure scenario: Order IDs are sequential (`nextOrderId++`, L684, L722), so an attacker enumerates them. For each active order, the attacker POSTs `{index: nextIndex, proof: <any fields>, signature: <random 65 bytes>}`. The Proof Verifier fails check 4 (`BadIssuerSignature`) and records `HELD`. The real carrier or sensor proof then arrives. Per L430, the agent does not ask for a release until the owner confirms. Automated settlement stops for every tenant, including the live demo order, at no cost to the attacker. With 300 tenants x 5 orders x 30 per hour, the attacker can also write about 45,000 `PROOF_RECEIVED` rows per hour into the single hash-chained ledger shared by all tenants (L155). Each row can carry an uploaded `document` of unspecified size, stored on the host volume.
- Impact: Remote denial of the core TradeFlow promise (S5 section 17: AI verifies and pays when conditions hold). Ledger and disk growth on the 512 MB host. Bank desk noise. No funds move.
- Architecture disposition: EXTEND. The seam is the Proof Verifier and the `/proofs` endpoint (S12 pipeline/validator, ledger).
- Minimal design change: Run the pure checks first: order exists and is active, `index == nextIndex`, `orderId`/`index`/`kind` match, and the signature recovers to `milestone.issuer`. A submission that fails any of these gets a 4xx and writes no ledger row, and it never changes milestone state. Only a proof validly signed by the milestone issuer can produce `PROOF_RECEIVED`, `HELD` (`BadProofTime`, `ConditionNotMet`, `DocumentMismatch`, `DeadlinePassed`) or a release. Cap the document size (for example 1 MB) and store only the document hash plus a bounded blob. Drop `ProofMismatch` and `BadIssuerSignature` from the HELD reason list, or keep them only as rejection codes.
- Acceptance check: New service test (extend T36/T40). An unsigned or wrongly signed proof is submitted for an active order, then a valid issuer proof is submitted. Before the change, the milestone is `HELD` and no Authorizer call happens (test fails). After the change, the first call returns 4xx with no ledger row, and the valid proof reaches `RELEASE_SIGNED`. A document above the cap returns 413.
- Confidence: High. The behaviour follows directly from L305, L327 and L429-430.
- What evidence would disprove it: A TD rule that a hold needs a valid issuer signature. I found none: L429 lists `BadIssuerSignature` as a hold reason.

## B3. The demo issuer keys merge the two release authorities into one process. The supervisor denylist leaks the keys to every child, including the Authorizer

- Proposed severity: High
- Source locator: S1 L334 ("live in the API process only"), S1 L799 (demo issuer row: "A release still needs the Authorizer"), S1 L188 and L75 (split authority, "two signatures"), S1 L812 (`INTERNAL_TOKEN` lets a caller ask the Authorizer to sign). Verified: S11 supervisor.py L19-37 (`SECRETS` denylist; `child_env` passes all other variables to every child).
- Scope link: TARGET T1 (release authority, key separation for TradeFlow, L799) and T2 (supervisor per-process keys as documented, L159, L265).
- Broken requirement or necessary assumption: The approved decision is that a release needs an issuer-signed proof and an Authorizer-signed authorization, with the keys separated by process (S1 L151, L180). This holds only if no single process holds both an issuer key and the ability to get an Authorizer signature.
- Concrete failure scenario: (a) `ISSUER_CARRIER_KEY`, `ISSUER_SENSOR_KEY` and `ISSUER_SURVEYOR_KEY` are added to `aegis.env`. They are not in `SECRETS`, so `child_env` gives them to the authorizer, executor, exit_agent and keeper processes. The Authorizer process then holds both signing keys for every web order, because every order takes its issuers from `GET /api/tradeflow/config` (L299). A compromise of that process alone releases every pending milestone of every tenant. (b) Even with a correct allowlist, the API process (internet-facing, runs the LLM, handles anonymous proof uploads) holds the issuer keys and `INTERNAL_TOKEN`. It can sign a "valid" proof for any order and call `/sign-release`. The Authorizer re-verifies, finds a correctly signed proof that meets the conditions, and signs. M12 tests only the existing secrets, and T1 to T47 have no test that the issuer keys stay in one process.
- Impact: The "split authority" claim (mechanism 5, L188) is false for every order the web creates. A one-process compromise pays every milestone early, including those held for a bad temperature, to the owner-chosen supplier. No funds go to a third party, but the security property that is presented to judges (30% weight) does not hold in the build.
- Architecture disposition: EXTEND. The seams are supervisor `OWNED`/`SECRETS` (S11) and `KEY_ENV` (S13). The issuer role is NEW.
- Minimal design change: (1) Change `child_env` to an allowlist per process (each process gets only the variables named in `OWNED[name]` plus a fixed non-secret set), or at minimum add the three `ISSUER_*_KEY` names to `SECRETS` and to `OWNED["api"]` only. (2) In S1 L799 and L814, state that for demo orders a compromise of the API process alone is enough to release, and say why this is accepted (testnet stand-in). As an alternative that keeps the claim true, run the demo issuers in a separate small process with its own internal token, so that the API process can only ask it to sign for orders where the session Safe is the buyer.
- Acceptance check: Extend M12. Start the supervisor with all `ISSUER_*_KEY` set and assert that only the API child environment (or only the issuer process environment) contains them. Before the change, the authorizer child has them (test fails). After the change, it does not. Add a T33 variant: an adversary that holds the API process secrets (issuer keys plus `INTERNAL_TOKEN`) is in scope, and the TD text names that result.
- Confidence: High for (a), because the code is verified. Medium for (b) as a severity driver.
- What evidence would disprove it: A plan in the TD to list issuer keys in `SECRETS`/`OWNED`, or an allowlist already in the supervisor (not present at HEAD).

## B5. The release pipeline has no terminal failure state. A deterministic preflight failure leads to an unbounded loop of re-sign and resubmit

- Proposed severity: Medium
- Source locator: S1 L304 (Executor runs `checkRelease` and a final signed `eth_call`), S1 L419-420 (`RELEASE_SUBMITTED -> RELEASE_REVERTED -> PROOF_RECEIVED`), S1 L432 (OutOfOrder rule). Verified: S11 executor.py L41-63 (a failed preflight sets the submission to `failed`; one serial queue; up to 60 s receipt wait per item, L14).
- Scope link: TARGET T1 (milestone state machine, Executor and Authorizer interaction).
- Broken requirement or necessary assumption: "Fail closed" (L91), and every terminal state writes one ledger row (L433). The design assumes that every release failure is transient.
- Concrete failure scenario: Some causes of a preflight failure do not heal on re-verification: an encoder difference such as int32 sign extension giving `BadSignature` on-chain while the Python recover passes, `BadProofTime` from clock skew (see B6), or `AuthorizationMismatch` from a `proofHash` that is computed differently. The design has no state for "preflight failed". If it maps to `RELEASE_REVERTED -> PROOF_RECEIVED`, the verifier passes again, the Authorizer signs a new nonce, and the preflight fails again, every cycle. Each loop writes ledger rows and Authorizer `signed` rows. If RPC lag lets a broadcast through, the Executor also spends gas on reverts. Transient causes also exist and are not specified. Under multi-tenant load, the serial Executor waits up to 60 s per receipt, so a queued 120 s authorization can expire before its turn (`Expired`). An Exit Agent quarantine bumps `policyVersion` for every tenant that holds shares (S6 L138), which gives `PolicyVersionMismatch` for every authorization in flight.
- Impact: A runaway loop that fills the ledger and the Authorizer DB and uses up the shared Executor's ETH (0.00019 ETH on 84532, S15 `balancesAfter`). The milestone never reaches a human. Observability is lost in the noise.
- Architecture disposition: EXTEND. The seams are the Executor submission kinds and the milestone workflow (S11 executor.py, S12 workflow.py).
- Minimal design change: Add a state `RELEASE_FAILED`. Classify preflight and receipt errors. `PolicyVersionMismatch`, `Expired` and `NonceUsed` (when no event exists) give at most 2 automatic re-sign attempts with a fresh authorization. `OutOfOrder` with an event means released (L432). Any other selector, or a third failure, goes to `HELD` with reason `ReleaseFailed:<selector>` and needs the owner. Give release submissions their own queue priority, or set the receipt wait below the authorization lifetime, so that a queued authorization does not expire.
- Acceptance check: A service test where `checkRelease` returns `BadSignature` for every attempt. Before the change, the Authorizer is called more than 3 times within N ticks (test fails). After the change, the milestone is `HELD` with `ReleaseFailed:BadSignature` after one attempt, with exactly one ledger row per transition. A second test bumps `policyVersion` once between signing and submission and expects one re-sign and then `RELEASED`.
- Confidence: Medium-High.
- What evidence would disprove it: A TD retry bound or a failure state for releases (none at L416-434).

## B6. Proof `issuedAt` uses wall-clock time but is checked against chain time, so a fresh demo proof fails `BadProofTime`

- Proposed severity: Medium
- Source locator: S1 L499 (algorithm 7 step 5 `order.createdAt <= proof.issuedAt <= now`), S1 L732 (release check 6 against `block.timestamp`), S1 L749 (`checkRelease` is a view at the latest block), S1 L328 (demo issuer signs on request). Verified: S11 authorizer.py L92 (Authorizer "now" is `chain.block_timestamp()`).
- Scope link: TARGET T1 (Proof Verifier, demo issuers, E6, live demo).
- Broken requirement or necessary assumption: The design assumes that a proof signed "now" passes `issuedAt <= block.timestamp` immediately. That is false when `issuedAt` is wall-clock time and the check runs against the latest mined block, which is 0 to 2 s old on Base, plus any host clock drift.
- Concrete failure scenario: The owner clicks "request demo proof (valid)". The demo issuer sets `issuedAt = int(time.time())` = T. The Proof Verifier, the Authorizer (chain time) or the Executor's `checkRelease` runs within 1 to 2 s against a block with timestamp T-1. Check 6 gives `BadProofTime`. If the verifier uses chain time, the milestone becomes `HELD` with `BadProofTime`, and B2's owner-confirmation rule then applies to the retry. If the verifier uses wall time, the Executor preflight fails and B5's loop starts. The E6 script hits the same problem when it signs and simulates at once.
- Impact: The happy-path demo fails at random, and the E6 recording can need retries on a day with no slack.
- Architecture disposition: EXTEND. The seams are the demo issuer signer and the Proof Verifier (S12 core), using the existing `chain.block_timestamp()` helper.
- Minimal design change: Specify that demo issuers set `issuedAt = min(wallNow, latestBlockTimestamp)`, clamped to at least `order.createdAt`. Specify that the Proof Verifier and the Authorizer compare against `chain.block_timestamp()`, never against wall time, the same as the Authorizer does for DAR expiry. In TD algorithm 7, write "now" as "latest block timestamp".
- Acceptance check: An Anvil integration test (part of T43). Sign a demo proof with `issuedAt = wall now` while Anvil's latest block timestamp is 2 s behind, then run the pipeline. Before the change, it gives `BadProofTime` (fails). After the change, it gives `RELEASED` in one attempt.
- Confidence: Medium. It depends on how the issuer sets `issuedAt`, which the TD does not specify. That gap is the problem.
- What evidence would disprove it: A TD rule that issuers use chain time, or that the issue time comes from the block of the order event.

## B7. The public order view and sequential order IDs contradict the tenant-isolation test T39 and expose off-chain proof data across tenants

- Proposed severity: Medium
- Source locator: S1 L326 (`GET /api/tradeflow/orders/{id}`: "a public read-only view for the supplier page", returning "Terms, milestone status, proofs and ledger references"), S1 L684 and L722 (sequential `orderId`), S1 L1054 (T39 "Tenant B cannot list, read, ... tenant A's orders"), S1 L92 and L239 (every query bound to the session's Safe).
- Scope link: TARGET T1 (API, T39) and T2 (isolation principle).
- Broken requirement or necessary assumption: The rule "Tenants share contracts, not authority. Every session, tool, query and stream event is bound to the session's Safe" (L92). T39 says reads are blocked, while L326 makes reads public.
- Concrete failure scenario: An unauthenticated client iterates `GET /api/tradeflow/orders/1..N`. Each response includes the off-chain data: uploaded documents or their metadata, hold reason codes, Verification Agent explanations, ledger references and the terms reference. On-chain data is public, but none of this off-chain data is. T39 cannot pass as written if the public view exists, or T39 passes only because it does not test the unauthenticated path.
- Impact: Cross-tenant leakage of business evidence and agent explanations, in the category that the TD lists as mitigated ("Cross-client data extraction", L830). The spec is inconsistent, so the implementer will guess on 18 Oct.
- Architecture disposition: EXTEND. The seam is session scoping (S10 sessions.py, S4).
- Minimal design change: Split the endpoint. A public `GET /api/tradeflow/orders/{id}/public` returns only fields that can be read on-chain (buyer, supplier, total, milestone amounts, statuses, tx hashes). The session-bound `GET .../{id}` returns proofs, documents, hold reasons, explanations and ledger references, only to the buyer's owner or bank session. State in T39 that unauthenticated reads get only the public shape.
- Acceptance check: Extend T39. An unauthenticated request and a tenant B owner session request for tenant A's order. Before the change, the response contains `proofs`/`ledgerRefs`/explanation fields (fails). After the change, only the on-chain field set is returned, and the full view returns 403/404.
- Confidence: Medium-High.
- What evidence would disprove it: A TD field list for the public view that excludes off-chain data.

- Proposed severity: Medium
- Source locator: S1 L336 (DeployTradeEscrow "adds the keys ... without changing any existing key"), S1 L889 (add issuer keys, rebuild the service, redeploy the web), S1 L1105-1110 (deploy and freeze on the same day; "After the freeze, the hosted service changes only by rollback"). - What evidence would disprove it: An existing Makefile or deploy step that chains the two scripts, and lazy, optional loading of the issuer keys in the plan.

## GAPs (depend on an unknown external fact)

- G1. Owner gas for the new TradeFlow transactions. Each owner burner gets 0.00005 ETH once ever (S1 L212, S10 onboarding.py L83-125). The design adds the funding transaction (MultiSend with `approve` and `createOrder`, which stores about 15 to 20 new slots), floor updates for linked obligations, and `waive`/`refund`.
